# Write like a human

Documentation should sound like one engineer explaining things to another over their shoulder - not like a spec generated by a committee. Apply these rules whenever you write prose for the project.

## Voice

- Use contractions naturally ("doesn't", "you'll", "it's"). Stiff formal prose is an instant giveaway.
- Prefer active voice and second person: "You'll need JDK 17", not "JDK 17 is required".
- It's fine to use "we" for project decisions ("We compile everything once at load because..."), but don't overdo it.
- Vary sentence length. Mix short punchy sentences with longer ones. If three consecutive sentences have the same rhythm, rewrite one.
- An occasional aside or opinion is welcome: "(this trips people up more often than it should)". One or two per document, no more.

## Structure

- Lead with what the thing does and why, before how it works internally.
- Skip the boilerplate. No "This document describes...", no "Overview" sections that just repeat the title, no "Conclusion" recaps.
- Use lists only for genuinely list-shaped things (steps, requirements). Paragraphs explain reasoning better than bullet fragments do.
- Code examples beat descriptions of code. Show real values from this repo, not `foo`/`bar` placeholders where avoidable.
- Headings should be scannable but plain: "Adding an accent", not "Leveraging the Accent Authoring Workflow".

## Honesty

- Document limitations and gotchas plainly. Readers trust docs that admit rough edges far more than docs that pretend everything is perfect.
- Don't hedge everything into mush. Pick a position and state it; note exceptions once.
- Never invent features, flags, or file paths that don't exist. Check the tree before referencing it.

## Anti-patterns (these scream "machine wrote this")

- Emoji bullets, bolded-every-noun, or exclamation-mark enthusiasm.
- Every section exactly three bullets long. Perfectly parallel headings.
- "In today's fast-paced world..." openings, or restating the obvious ("Git is a version control system").
- Repetitive transitions: "Additionally", "Furthermore", "Moreover" stacked in one paragraph.
- Em-dash overload; prefer commas, parentheses, or just shorter sentences.
